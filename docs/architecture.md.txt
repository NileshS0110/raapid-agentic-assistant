
# Employee AI Assistant – Architecture and Design
## RAAPID Agentic AI Assignment

### 1. Executive Summary

The Employee AI Assistant is a lightweight, locally runnable prototype that handles three categories of employee requests:

1. Policy and process questions using retrieval-augmented generation (RAG).
2. Structured employee-record queries using mock HR data and deterministic Python tools.
3. Action requests such as ticket creation, with sensitive actions routed through human review.

The architecture uses Python for orchestration, Streamlit for the user interface, Ollama with Qwen2.5 3B for local language generation, Ollama all-minilm for embeddings, NumPy for similarity search, Pydantic for schema validation, and JSON files for mock enterprise data.

The design deliberately separates deterministic business rules from LLM-generated responses to improve predictability, traceability and control.

### 3. Core Components and Technology Choices

| Component | Technology | Responsibility |
|---|---|---|
| User interface | Streamlit | Employee-facing chat interface |
| Orchestration | Python | Coordinates routing, tools, retrieval and responses |
| Input/output validation | Pydantic | Enforces structured request and response schemas |
| LLM | Qwen2.5 3B via Ollama | Generates grounded policy answers |
| Embeddings | all-minilm via Ollama | Converts documents and queries into vectors |
| Similarity search | NumPy cosine similarity | Retrieves relevant knowledge chunks |
| Knowledge base | Markdown files | Stores policy and process documents |
| Structured records | JSON | Mock employee, leave, reimbursement and asset data |
| Evaluation | Python evaluator and pytest | Tests behaviour and records pass/fail results |

A simple Python orchestrator was selected instead of a multi-agent framework. This keeps the prototype easy to inspect, debug and explain while retaining explicit branching and tool execution.

### 4. Request Intake and Routing

The employee submits a natural-language request through Streamlit.

The request is validated using Pydantic and passed to the orchestrator.

Before routing, deterministic checks identify:
- Suspicious prompt-injection phrases.
- Requests attempting to access another employee's records.
- Multiple conflicting intents.
- Requests too vague to process safely.

A deterministic keyword-based router then selects one of three workflows:

**Policy question:** Routed to the RAG pipeline.

**Record query:** Routed to structured employee data tools.

**Action request:** Routed to the action workflow.

If the request is incomplete or ambiguous, the assistant asks the employee for clarification.

The LLM does not independently decide authorization or execute unrestricted business actions.

### 5. Retrieval-Augmented Generation

The knowledge base contains nine Markdown documents covering leave, expenses, finance FAQs, security, onboarding, assets, remote work and travel.

**Document processing**

- Extract document metadata, including document ID, version, status and effective date.
- Split document text into chunks of 180 words with 30-word overlap.
- Generate 384-dimensional embeddings using all-minilm through Ollama.
- Store chunk text, metadata and embeddings in a local JSON vector store.

The current documents each fit within a single chunk, so the configured chunk-overlap behaviour is not exercised by the present dataset.

**Retrieval**

1. Generate an embedding for the employee's query.
2. Exclude documents whose status is not current.
3. Calculate cosine similarity against the remaining document vectors.
4. Sort results by similarity.
5. Retrieve the top two chunks.
6. Apply relevance and conflict checks.
7. Construct a context limited to 300 words.
8. Pass the context to Qwen2.5 3B for grounded answer generation.

**Version control**

Document status metadata is used as a deterministic filter before ranking. This prevents superseded policy documents from entering the answer context.

The regression experiment demonstrated why this control matters: disabling the filter caused E02 to fail because the superseded LEAVE-2024 source was cited.

**Conflict handling**

The prototype includes an explicit check for the seeded conflict between the Employee Expense Policy and Finance FAQ regarding meal reimbursement limits.

When both conflicting values are retrieved, the assistant surfaces the disagreement and advises confirmation with Finance.

**Abstention**

If retrieval confidence is below the configured threshold, or no relevant context is found, the assistant abstains rather than inventing an answer.

The current confidence threshold is 0.30 and remains a prototype setting requiring broader calibration.

### 6. Structured Data and Action Tools

Structured employee information is stored in JSON files:

- Employee records.
- Leave balances.
- Reimbursement claims.
- Assigned assets.
- Tickets.
- Human-review requests.

The Python tool layer exposes separate functions for leave, reimbursement and asset queries.

Before returning employee information, the tool checks that the authenticated session employee matches the requested employee.

Action workflows include:

- Ticket creation.
- Required-field validation.
- Priority validation.
- Duplicate prevention through request IDs.
- Error handling when a tool fails.
- Human-review submission for sensitive actions.

The current prototype uses a fixed demonstration employee ID. In production, this identity must come from a trusted SSO/JWT session rather than a hardcoded value or employee-supplied text.

### 7. Human-in-the-Loop and Responsible AI

Sensitive actions, such as updating bank details, are not executed automatically.

Instead, the system creates a pending human-review record containing the employee, requested action, details and reason for escalation.

Other safeguards include:

- Employee-level access checks.
- Prompt-injection phrase detection.
- Structured input validation.
- Restricted action tools.
- Policy-source citations.
- Relevance checks and abstention.
- Graceful tool-failure responses.

The prototype's phrase-based prompt-injection detection is not a comprehensive security solution. Production deployment would require stronger identity, authorization, input-security and audit controls.

### 8. Evaluation and Quality Assurance

The evaluation suite contains 24 scenarios, including all six mandatory cases.

It uses deterministic assertions for:
- Response status.
- Routing decision.
- Required and forbidden terms.
- Required and forbidden citations.
- Human-review flags.
- Tool outcomes.

No LLM-as-judge is used, so model-judge calibration and agreement scoring are not applicable.

**Final evaluation results**

- Total scenarios: 24
- Passed: 24
- Failed: 0
- Overall pass rate: 100%
- Mandatory scenarios: 6/6 passed

**Regression experiment**

The current-versus-superseded filter was deliberately disabled.

| Run | Passed | Failed |
|---|---:|---:|
| Working baseline | 24 | 0 |
| Broken version | 23 | 1 |
| Restored version | 24 | 0 |

E02 detected the appearance of the superseded LEAVE-2024 citation.

**Retrieval evaluation**

A labelled set of ten queries achieved:

- Hit Rate@2: 100%
- Recall@2: 100%
- Precision@2: 70%

These results are based on a small, manually labelled prototype dataset and should not be interpreted as production retrieval performance.

### 9. Performance, Cost and Scalability

The prototype runs locally using Ollama, without paid external LLM or embedding API calls.

Measured median end-to-end latency:

| Workflow | Median latency |
|---|---:|
| Policy question | 6,076.59 ms |
| Structured record query | 0.58 ms |
| Ticket creation | 9.28 ms |

The policy workflow is slower because it requires local embedding generation and LLM inference.

The prototype has no external API usage cost, although local electricity, hardware and maintenance have costs.

**Scaling limitations**

- Local LLM inference is the primary latency bottleneck.
- JSON files are unsuitable for concurrent production transactions.
- No distributed task queue or production concurrency management.
- No embedding cache.
- Vector-store updates require manual rebuilding.
- No load test has been conducted.

A production implementation would consider managed databases, a scalable vector database, enterprise identity integration, asynchronous processing, observability and controlled LLM infrastructure.

### 10. Known Limitations and Future Improvements

1. Replace the fixed demonstration identity with enterprise SSO.
2. Replace JSON mock records with authenticated enterprise APIs and transactional databases.
3. Expand the knowledge base and test actual multi-chunk retrieval.
4. Calibrate retrieval confidence against a larger labelled dataset.
5. Generalize conflict detection beyond the seeded meal-limit example.
6. Introduce stronger prompt-injection and data-loss prevention controls.
7. Add production monitoring, audit logs and concurrency testing.
8. Introduce a proper human approval interface and workflow.
9. Benchmark latency under concurrent load.
10. Add automated vector-store refresh when policies change.

---

### Conclusion

The prototype demonstrates a controlled employee-assistance architecture combining deterministic workflow orchestration, retrieval-grounded policy responses, structured data tools, explicit human review and automated evaluation.

The design prioritizes predictable routing, authorization boundaries, source traceability and graceful failure handling over unnecessary agent complexity.
